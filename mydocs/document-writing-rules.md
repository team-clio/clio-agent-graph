# 공통 문서 작성 규칙

이 문서는 Clio 프로젝트에서 작성하는 모든 글에 공통으로 적용한다.

## 적용 범위

- GitHub Issue의 제목·본문·댓글
- Pull Request의 제목·본문·리뷰·댓글
- `README`, `docs`, `mydocs` 아래의 모든 문서
- 작업 계획, 결정 기록, 결과 보고, 회고 등 저장소에서 관리하는 글

문서 종류별 템플릿이나 별도 규칙이 있으면 함께 적용한다. 별도 규칙과 이 문서가 충돌하면
더 구체적인 규칙을 따르되, 변경 이유와 적용 범위를 문서에 명시한다.

## 문서 작성의 8가지 원칙

### 1. 독자의 관점에서 작성한다

- 문서는 작성자가 아닌 독자의 관점에서 작성한다.
- 단순히 읽기 좋은 문서보다 필요한 정보를 빠르게 찾고 참조하기 좋은 문서가 되도록 구성한다.
- 독자가 내용을 편안하게 이해할 수 있도록 정중하고 명확한 표현을 사용한다.
- 작성자가 알지 못하는 내용이나 아직 결정되지 않은 사항도 비워두지 않고 `확인 필요`, `미정`,
  `담당자 협의 필요` 등으로 상태를 명시한다.
- 불필요하게 어려운 표현을 피하고 함께 일하는 사람들이 공통으로 이해할 수 있는 용어를 사용한다.

### 2. 불필요한 반복을 피한다

- 하나의 정보는 가능한 한 한 곳에서만 관리한다.
- 같은 정보를 여러 곳에 기록하여 수정이 어려워지거나 내용이 달라지지 않도록 한다.
- 다른 문서나 항목의 정보가 필요하면 내용을 그대로 반복하기보다 링크나 참조 위치를 제공한다.
- 반복을 피하기 위해 독자가 지나치게 많은 문서를 찾아봐야 한다면 이해에 필요한 핵심 정보는
  다시 제공할 수 있다.

### 3. 모호함을 피한다

- 업무 전에 확인하거나 결정할 사항을 정리하여 구성원들이 같은 방향으로 판단할 수 있게 한다.
- 상황에 따라 여러 해석이 가능하고 모든 해석이 문서 목적에 부합한다면 허용할 수 있다.
- 잘못된 해석으로 이어질 가능성이 있으면 조건·범위·예외·사례를 추가하여 의미를 명확히 한다.
- 조직에서 일반적으로 사용하지 않는 용어나 표기법에는 의미와 사용 방법을 함께 설명한다.

### 4. 일관된 구성을 사용한다

- 같은 종류의 문서는 합의된 표준 구조와 형식을 사용한다.
- 제목, 목차, 용어, 날짜, 상태 표시 등의 작성 방식을 일관되게 유지한다.
- 독자가 문서 구성에 익숙해져 필요한 정보를 빠르게 찾을 수 있게 한다.
- 기존 표준과 다른 구성이 필요하면 변경 이유와 적용 범위를 명시한다.

### 5. 결정의 근거를 기록한다

- 최종 결정뿐 아니라 결정을 내린 배경과 근거도 기록한다.
- 검토했지만 선택하지 않은 대안과 제외한 이유도 남긴다.
- 당시의 제약 조건과 판단 기준을 기록하여 같은 내용을 반복해서 논의하지 않게 한다.
- 결정 이후 조건이 달라졌을 때 기존 결정을 다시 검토해야 하는지 판단할 수 있게 한다.

### 6. 지속적으로 개정하되 지나친 수정은 피한다

- 문서에는 현재 상황과 정확한 정보를 반영한다.
- 오래되거나 실제와 다른 내용을 방치하여 문서의 신뢰도를 떨어뜨리지 않는다.
- 변경이 발생하면 중요도와 영향 범위에 따라 문서를 갱신한다.
- 작은 변화까지 즉시 반영하느라 지나치게 많은 비용을 쓰지 않도록 정해진 개정 주기나 버전 관리
  기준에 맞춰 수정한다.
- 주요 변경에는 변경일, 변경 내용, 변경 이유를 남겨 이력을 확인할 수 있게 한다.

### 7. 문서의 목적에 맞게 리뷰한다

- 문서를 작성하기 전에 예상 독자와 이해관계자를 명확히 정의한다.
- 배포 전에는 실제 독자에게 정확성, 이해 가능성, 정보의 충분성, 실제 활용 가능성을 검토받는다.
- 리뷰 참여자와 주요 의견, 반영 여부를 기록하여 이후 변경 과정을 확인할 수 있게 한다.

### 8. 문서는 200줄을 넘기지 않는다

- 한 문서가 200줄을 넘으면 독자가 필요한 정보를 찾기 어렵고 변경 범위도 커진다.
- 200줄 제한은 불필요한 설명과 반복을 줄이기 위한 기준이다. 먼저 문장을 줄이고 구조를 단순화한다.
- 같은 목적·독자·읽기 흐름을 가진 내용을 줄 수만 맞추려고 여러 파일로 나누지 않는다.
- 목적이나 독자가 다르고 각 문서를 독립적으로 참조할 수 있을 때만 분리한다.
- 분리로 탐색 비용이 커진다면 나누지 않고 핵심 결정·근거·결과만 남긴다.

## 작성·리뷰 체크리스트

- [ ] 예상 독자와 문서의 목적이 분명한가?
- [ ] 독자가 필요한 정보를 빠르게 찾을 수 있는가?
- [ ] 미정인 내용에 상태가 표시되어 있는가?
- [ ] 다른 문서의 정보를 불필요하게 복제하지 않았는가?
- [ ] 조건·범위·예외가 명확한가?
- [ ] 같은 종류의 문서와 구조·용어·표기가 일관적인가?
- [ ] 결정의 배경·근거·대안·제약 조건이 기록되어 있는가?
- [ ] 변경된 사실과 주요 변경 이력이 반영되어 있는가?
- [ ] 실제 독자 또는 이해관계자의 리뷰가 필요한가?
- [ ] 전체 문서가 200줄 이하인가?
- [ ] 문서 분리가 줄 수 제한을 피하기 위한 형식적인 분리가 아닌가?
