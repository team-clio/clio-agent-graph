# 코드 검색 결과 순서 — Plan

> 승인: 2026-10-11

## 확인한 사실

- 배포 Agent 이미지의 git은 2.47.3이다. `git grep --max-count`(파일당 매칭 수 제한, 2.38+)를 쓸 수 있다.
- Finvibe 저장소에서 흔한 검색어도 전체 매칭 수집은 가볍다. `get` 3,569줄 48ms, `return` 2,225줄 25ms.
- 파일 구성: `.java` 682, `.md` 61, `.js` 25, `.txt` 18, `.json` 14, `.yml` 13 등.
- `RepositoryService.search`는 `RepositorySearchHit` 목록을 반환한다. 호출자는 `search_code` 노드와
  `search_repository_code` Tool 두 곳이다.
- Finvibe의 #13 원인 문서(`docs/tasks/minute-candle-query-performance/01-overview.md`)도 검색 대상이다. 문서는
  때로 정답을 직접 담고 있으므로 완전히 버리면 손해가 있다.

## 구현 단계

1. 파일 분류: 검색 대상 파일을 소스·테스트·문서 등으로 나누는 규칙을 둔다(D2).
2. 결과 정렬과 상한: 전체 매칭을 모아 분류 우선순위와 파일당 상한으로 고른다(D1, D3, D4).
3. 잘림 정보: 검색 결과에 전체 매칭 수와 잘림 여부를 담아 Tool 응답에 노출한다(D5).
4. 평가: 개선 전후를 비교한다(D6).
5. 문서: `convention/architecture.md`의 repository 검색 설명을 갱신한다.

각 단계는 해당 결정이 내려진 뒤 구현하고, 결정 단위로 커밋한다.

## 결정 포인트

### D1. 결과 정렬 기준

- A. 파일 분류 우선순위(소스 → 테스트 → 설정 → 문서) 다음 경로 순.
- B. 관련성 점수(파일 내 매칭 수, 식별자 경계 일치, 경로에 검색어 포함 등)로 정렬.
- C. A의 분류 우선순위 안에서 파일 단위로 번갈아 채운다(round-robin). 한 파일이 상한을 독차지하지 않는다.

추천: C. 결정적이고 설명하기 쉬우며, overview의 문제 1·2를 함께 해결한다.
기각 조건: 같은 분류 안에서 관련 없는 파일이 앞서는 일이 평가에서 자주 보이면 B의 점수를 분류 안 정렬에 더한다.

### D2. 파일 분류 판정

- A. 확장자와 경로 규칙. 문서는 `.md .mdx .rst .adoc .txt`, 테스트는 경로 조각 `test/ tests/ __tests__/ spec/`
  또는 파일명 `*Test.* *_test.* test_*.* *.spec.*`, 설정은 `.json .yml .yaml .toml .xml .properties .gradle`,
  나머지는 소스.
- B. GitHub Linguist 같은 외부 분류기를 쓴다. 정확하지만 의존성과 이미지 크기가 늘어난다.
- C. 저장소 등록의 include/exclude 설정만 쓴다. 사용자가 설정하지 않으면 지금과 같다.

추천: A. 기각 조건: 확장자만으로 소스와 문서가 갈리지 않는 저장소(예: 문서 사이트 생성기)가 주요 대상이면 B를 검토한다.

### D3. 문서 매칭의 취급

- A. 후순위로 둔다. 소스·테스트·설정이 상한을 채우지 못하면 문서가 들어온다.
- B. 기본 제외하고, Tool 인자(`include_docs`)로만 포함한다.
- C. 결과를 `code`와 `docs` 그룹으로 나눠 각각 일부를 돌려준다.

추천: A. 문서가 정답을 담는 경우를 살리면서 코드가 밀리지 않는다.
기각 조건: 평가에서 문서가 여전히 상위 인용을 차지하면 C로 문서 몫을 고정한다.

### D4. 파일당 상한

- A. 파일당 2줄
- B. 파일당 3줄
- C. 상한 없음(정렬만 바꾼다)

추천: A. 기본 `limit` 20에서 최소 10개 파일을 보여 준다. 분석 Agent는 `read_repository_file`로 필요한 파일을 더 읽을 수 있다.
기각 조건: 한 파일의 여러 위치가 함께 필요해 Agent가 같은 파일을 반복 검색하는 일이 많으면 B로 늘린다.

### D5. 잘림 정보 노출

- A. 검색 결과에 `total_matches`, `truncated`를 추가하고 Tool 응답에 그대로 노출한다. `search` 반환 타입이 바뀐다.
- B. 로그·metric에만 남긴다. Agent의 검색 전략에는 영향이 없다.
- C. 노출하지 않는다.

추천: A. Agent가 검색어를 좁히거나 파일을 직접 읽도록 판단할 근거가 된다.
기각 조건: 반환 타입 변경이 다른 진행 중 브랜치(KAN-23 등)와 충돌이 크면 기존 목록 반환을 유지하고 별도 메서드로 메타데이터를 준다.

### D6. 평가 방법

- A. Finvibe 실제 버그 3건 재분석(원인 파일 인용 여부, Java 인용 수) + clio-benchmark fixture 회귀(코드 위치 점수).
- B. Finvibe 3건만.
- C. 단위 테스트만.

추천: A. 실제 대형 저장소 개선과 기존 fixture 회귀를 함께 본다.
기각 조건: clio-benchmark는 Server internal API(8080)가 노출된 스택이 필요하다. 체험 스택은 3000만 열려 있으므로
준비 비용이 크면 B로 줄이고 fixture 회귀는 후속으로 남긴다.
