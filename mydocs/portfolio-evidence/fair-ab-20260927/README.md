- 실행일: 2026-09-27
- 상태: 단일 사례·프로필별 5개 예정 회차 완료
- 목적: 검색·검증 파이프라인이 분석 품질, 변동성, 지연, 실행 신뢰성에 미치는 영향을 분리한다.

- 사람 리뷰: 리뷰 필요

## 결론

full-clio가 평균 점수를 높였다는 가설은 이번 반복 실험에서 확인되지 않았다.
성공 실행 기준 평균은 one-shot 96.51점, full-clio 96.25점으로 사실상 같았다.

대신 full-clio는 최저 점수를 86.67점에서 94.17점으로 높이고 표준편차를
5.78에서 2.76으로 줄였다. 코드 위치 식별도 평균 90%에서 100%로 개선됐다.
즉 이번 결과가 지지하는 주장은 **평균 향상**이 아니라 **성공 실행의 품질 하한과
코드 근거 일관성 개선**이다. 그 대가로 평균 지연은 2.01초(6.1%) 증가했다.

## 비교한 파이프라인

- one-shot: 코드 검색 후 분석·계획·위험 평가·저장
- full-clio: 문서·코드·이력 검색 후 분석·계획·Quality Gate·위험 평가·저장
- 단순 프로필은 CLIO_BENCHMARK_MODE=true일 때만 실행된다.

따라서 두 평균은 표본 수가 달라 우열을 확정하는 용도로 사용하지 않는다.

## 실행 신뢰성

| 지표 | one-shot | full-clio |
|---|---:|---:|
| 첫 시도 성공 | 3/5 (60%) | 4/5 (80%) |
| 재시도 후 예정 회차 완료 | 5/5 (100%) | 4/5 (80%) |
| 전체 실제 시도 | 7 | 8 |
| 동기화 실패 | 2 | 4 |

실패는 모두 repository sync 단계에서 발생했다. 진단 로그에서는 생성 모델의
logical key 중복과 필수 필드가 빠진 update payload가 확인됐다. 이 결과는 분석
품질과 별도로 동기화 멱등성·중복 정규화·구조화 출력 재시도가 다음 개선
우선순위임을 보여준다.

## 원본 증거

- 1회차 원본: one-shot/, full-clio/
- 2~5회차 성공 원본: repetitions/{profile}/r{n}/
- 실패 manifest: failed-attempts/{profile}/
- 집계값: aggregate.json
- 각 성공 원본에는 실행 설정, revision, 결과, 차원별 판정, fixture commit이 포함된다.

## 해석 한계와 다음 결정

- 사례가 1건이므로 다른 결함 유형으로 일반화하지 않는다.
- PCM 동기화 방어를 추가한 최종 revision 080774b는 독립 실행 4/4를 완료했다.
  상세 원본은 post-fix-validation/에 있으며, 30건 평가셋에서도 재검증이 필요하다.
- 재현 계획과 불확실성 점수 하락 원인을 프롬프트·Quality Gate 규칙별로 분해한다.
- 두 프로필 모두 verification endpoint의 read-only transaction 오류가 있어 별도 수정이 필요하다.
- 토큰·모델 호출 수가 summary에 연결되지 않아 비용은 현재 지연 시간만 비교했다.

## 후속 개선

repository sync 실패를 계기로 다음을 구현했다.

- 구조화 출력 검증 시 최대 3회까지 오류 피드백 기반 재생성
- commit 검증 실패 시 최신 PCM snapshot과 후보를 다시 조회한 뒤 재생성
- create와 update/no_change의 비활성 식별자를 경계에서 안전하게 정규화
- operation별 필수·금지 필드를 프롬프트에 명시

최종 revision 080774b의 독립 환경 4회는 모두 repository sync와 분석을 완료했다.
이는 제한된 검증 구간의 결과이며, 장기 성공률로 일반화하지 않는다.
