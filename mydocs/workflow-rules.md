# 작업 절차 규칙

이 문서는 clio의 작업이 따르는 절차다. **모든 작업에 자동으로 적용되지는 않는다.**
적용 여부는 작업을 시작하기 전에 사용자에게 물어 결정한다(아래 [적용 여부 확인](#적용-여부-확인-opt-in)).

적용하기로 한 작업에서는 AI(Claude)가 이 규칙을 **위배하지 않는다.** 예외가 필요하면
진행하기 전에 사용자에게 명시적으로 확인받는다.

Issue, PR, `README`, `docs`, `mydocs` 등 모든 글은
[`document-writing-rules.md`](document-writing-rules.md)의 공통 문서 작성 규칙도 함께 따른다.
저장소별 코드 배치 규칙은 각 저장소의 코드 컨벤션 문서를 따른다.

## 대원칙

> **결정은 언제나 사용자가 한다. AI는 선택지를 제시하고 추천할 뿐, 사용자를 대신해 결정하지 않는다.**

"알아서 해줘"라고 명시적으로 위임받은 경우가 아니면, 결정 포인트에서 임의로 고르고 넘어가지 않는다.
위임받았더라도 무엇을 어떻게 정했는지 decision 파일에 남긴다.

## 적용 기준

| | 작업 |
|---|---|
| **적용** | 새 기능·도메인 추가 / 공개 API·DB 스키마·서비스 간 계약 변경 / 되돌리기 어려운 결정이 1개 이상 있는 작업 / 여러 레이어·패키지에 걸친 리팩터링 |
| **미적용** | 단건 버그 수정 / 오타·포맷·주석 / 테스트 추가 / 문서 수정 / 의존성 버전 업 |

애매하면 적용 쪽으로 묻는다. 미적용 작업이 진행 중 적용 기준에 들어가면 그 시점에 다시 묻는다.

## 적용 여부 확인 (opt-in)

작업의 첫 파일 변경 전에 AI가 **반드시 먼저 묻는다.** 사용자가 답하면 그 결과를
`.claude/workflow-mode.json`에 현재 브랜치 이름으로 기록한다.

```json
{ "task/pcm-inspect-ui": "on", "main": "off" }
```

- `on` — 이 브랜치의 작업에 이 문서의 절차를 적용한다.
- `off` — 적용하지 않는다. 절차 없이 바로 작업한다.

기록이 없으면 `.claude/hooks/workflow-gate.py`(PreToolUse hook)가 파일 변경과 커밋을 차단한다.
차단은 "아직 묻지 않았다"는 뜻이며, 묻고 기록하면 그 브랜치에서는 다시 묻지 않는다.
결정을 바꾸려면 해당 브랜치의 값을 수정한다.

## 산출물 구조

작업 하나당 폴더 하나: `mydocs/task-<이름>/`

```
01-overview.md    작업 배경·현재 상태·문제·개선 방향·범위
02-plan.md        구현 단계 + "사용자가 결정할 항목(결정 포인트)"을 명시
03-decisions.md   결정 히스토리 (D1, D2, ... / F1, F2, ...)
04-result.md      최종 변경 요약·테스트 결과·남은 과제
```

작업의 완료 상태와 남은 과제는 해당 작업의 `04-result.md`에서 관리한다.

## 단계별 절차와 게이트(gate)

각 단계는 **사용자 컨펌 없이는 다음 단계로 넘어가지 않는다.**
컨펌을 받으면 해당 문서 맨 위에 승인 줄을 추가하고 그 상태로 커밋한다. 커밋이 곧 승인 시각의 증거다.

```markdown
> 승인: 2026-08-24
```

### 1단계. Overview

- `01-overview.md`를 작성한다.
- **게이트: 사용자가 overview를 컨펌해야 다음으로 넘어간다.**
- 승인 줄 추가 후 커밋: `docs: <작업> overview`

### 2단계. Plan

- `02-plan.md`를 작성한다. 구현 단계와 함께 **사용자가 결정해야 할 항목(결정 포인트)**을
  빠짐없이 목록으로 담는다. 각 결정 포인트에는 대안을 적는다.
- AI 추천을 적을 때는 **그 추천이 틀리는 조건(기각 근거)도 함께** 적는다. 추천만 적으면
  사용자 결정이 승인 절차로 형식화된다.
- **게이트: 사용자가 plan과 "결정 포인트 목록"을 컨펌해야 다음으로 넘어간다.**
- 승인 줄 추가 후 커밋: `docs: <작업> 구현 계획`

### 3단계. Decisions (하나씩 결정하며 진행)

- plan의 결정 포인트를 **하나씩** 사용자에게 물어 결정한다.
- 결정될 때마다 `03-decisions.md`에 히스토리로 남긴다(무엇을·왜 골랐는지, 제외한 대안).
- **결정 하나(또는 그 결정에 따른 구현 한 조각)를 끝낼 때마다 커밋한다.**
  - 커밋 메시지만 봐도 무슨 결정을 반영한 작업인지 읽혀야 한다.
  - 커밋은 가능하면 컴파일/테스트가 통과하는 상태로 만든다.
- 아직 결정 안 된 항목을 앞질러 구현하지 않는다.

### 4단계. Result

- 모든 결정과 구현이 끝나면 `04-result.md`에 최종 결과를 남긴다.
- 완료한 범위, 검증 결과, 남은 과제와 후속 작업을 명시한다.
- 커밋: `docs: <작업> result`

## 결정 기록 규칙 (D / F)

- **D 항목** — plan의 결정 포인트에 대한 결정. plan에 있던 번호를 그대로 쓴다.
- **F 항목** — plan에 없던 후속·보완 결정. 다음 두 가지를 담는다.
  - 어떤 D의 보완인지 (`F1. ... (D3 보완)`)
  - 구현 중 발견해 결정이 필요해진 것 (`F2. ... (구현 중 발견)`)

F는 plan을 다시 쓰지 않고도 실제 전개를 기록하는 자리다. plan과 다르게 간 것을 F 없이 넘기지 않는다.

## 예외 경로

정상 경로에서 벗어날 때의 처리를 정한다. 어느 경우든 **말없이 벗어나지 않고 F 항목이나 result에 남긴다.**

| 상황 | 처리 |
|---|---|
| plan이 틀린 것으로 드러남 | 남은 결정 포인트를 F 항목으로 다시 정의하고 사용자 컨펌을 받는다. `02-plan.md`는 고치지 않고 `03-decisions.md`에 경위를 남긴다 |
| 범위가 커짐 | 쪼갤 지점을 사용자와 정하고 새 task 폴더로 분리한다. 원래 task의 `04-result.md`에 넘긴 범위를 적는다 |
| 작업 중단·폐기 | `04-result.md`에 중단 사유와 되살릴 때 필요한 정보를 적고 커밋한다. 폴더를 지우지 않는다 |
| 여러 task 병행 | task 하나당 브랜치 하나. 브랜치를 옮길 때 진행 중 결정을 먼저 `03-decisions.md`에 기록한다 |
| 두 저장소에 걸친 작업 | 계약을 **요청하는 쪽** 저장소에 task 폴더를 두고 결정을 모두 거기 기록한다. 반대쪽 저장소에는 변경 커밋만 남기고, 커밋 메시지에서 그 task 이름을 참조한다 |

## 커밋·브랜치 규칙

- **항상 `main`에서 새 브랜치를 판다.** 다른 feature 브랜치 위에 브랜치를 만들지 않는다.
  선행 작업이 곧 머지될 예정이면 머지를 확인하고 main 기준으로 시작한다.
- 브랜치 이름은 `task/<작업 이름>` 을 쓴다.
- **작업을 잘게 쪼개, 결정/하위작업 하나 완료 시마다 커밋한다.** 한 PR에 큰 덩어리 하나로 몰지 않는다.
- PR의 커밋 목록만으로 작업의 전개(overview → plan → 결정별 구현 → result)가 읽혀야 한다.

## 절대 하지 말 것 (위배 금지)

1. 적용 여부를 묻지 않고 작업을 시작하지 않는다.
2. overview/plan 컨펌 없이 구현으로 직행하지 않는다.
3. 사용자 결정 없이 결정 포인트를 임의로 정하고 진행하지 않는다(명시적 위임 제외).
4. 결정 히스토리(`03-decisions.md`)를 남기지 않고 넘어가지 않는다.
5. 여러 결정을 한꺼번에 묶어 큰 커밋 하나로 만들지 않는다.
6. main이 아닌 브랜치에서 브랜치를 파지 않는다.

## 체크리스트 (작업 시작 시 붙여넣고 사용)

```
[ ] 적용 여부 질문 → 사용자 답변 → .claude/workflow-mode.json 기록
[ ] task-<이름>/ 폴더 생성, main에서 task/<이름> 브랜치 분기
[ ] 01-overview 작성 → 사용자 컨펌 → 승인 줄 → 커밋
[ ] 02-plan 작성 (결정 포인트 목록 포함) → 사용자 컨펌 → 승인 줄 → 커밋
[ ] 결정 포인트 1개씩: 사용자 결정 → 03-decisions 기록 → 구현 → 커밋   (반복)
[ ] 04-result 작성 (완료 범위·검증 결과·남은 과제 포함) → 커밋
[ ] PR (base=main)
```
