Project Context Memory · Design Document

프로젝트를 기억하는
자동 지식 시스템

Clio의 PCM은 Markdown 지식을 정본으로 관리하고, hybrid search와 고정 snapshot을 통해 Agent에게 장기기억을 제공한다. 이 문서는 합의된 전체 설계와 첫 구현 단위를 하나의 실행 가능한 청사진으로 정리한다.

On-premise Single agent-server node PostgreSQL + pgvector External LLM & Embedding APIs Automatic active commits

Executive summary

PCM은 Vector DB가 아니라
프로젝트 장기기억 서비스다

PCM은 Graph 계층 아래의 service layer이며, Agent에는 읽기 전용 Tool을 제공한다. 사용자가 전달한 문서, 등록된 Repository, 해결된 이슈에서 지식을 자동으로 생성하고 계속 갱신한다. 사람은 저장소를 직접 편집하지 않고 Agent를 통해서만 접근한다.

01

Knowledge Markdown

주제 단위 프로젝트 지식. 내용의 canonical representation이며 revision과 provenance를 가진다.

02

Hybrid Index

pgvector 의미 검색과 PostgreSQL keyword·trigram 검색을 결합한 재생성 가능한 파생 인덱스다.

03

Repository Memory

commit으로 고정된 Git mirror. 지식 검색 후 실제 구현을 Agent가 탐색하고 검증하는 원본 코드다.

운영 모델: 모든 유효한 변경은 사람 승인 없이 즉시 active가 된다. 다만 스키마, source reference, base revision 검증을 통과한 완결된 commit만 활성화된다.

Decisions

변하지 않는 설계 원칙

정본과 파생 데이터

  • Markdown은 PCM 지식 내용의 정본이다.
  • PostgreSQL은 identity, revision, transaction 상태의 정본이다.
  • Vector·keyword index는 언제든 다시 만들 수 있는 파생 데이터다.
  • Git mirror는 외부 Repository 특정 commit의 로컬 표현이다.

자동화와 안전성

  • 승인 대기나 수동 편집 흐름을 만들지 않는다.
  • Agent는 구조화된 변경안을 만들고 Service가 revision을 commit한다.
  • 과거 revision은 보존하며 삭제는 tombstone revision으로 표현한다.
  • 불일치는 격리하지 않고 출처와 의미를 포함한 active 지식으로 기록한다.

접근과 권한

  • Agent에는 읽기 Tool만 제공한다.
  • 지식·인덱스·Repository 쓰기는 Graph Node만 수행한다.
  • Tool의 project와 snapshot은 Graph가 바인딩한다.
  • Agent가 filesystem path, project ID, commit을 임의 선택하지 못한다.

일관성과 재현성

  • 분석 시작 시 PCM revision과 Repository commit을 고정한다.
  • 모든 주장과 지식은 provenance를 가진다.
  • 동일 source event는 한 번만 commit된다.
  • revision 충돌은 최신 지식에서 change set을 다시 생성한다.

Hybrid ranking

pgvector와 keyword 검색 결과는 점수 척도를 직접 섞지 않고 Reciprocal Rank Fusion으로 결합한다.

final_score = 1 / (60 + vector_rank)
            + 1 / (60 + keyword_rank)

  • pcm_commits — 원자적 변경 단위

  • pcm_chunk_embeddings — generation별 vector

Snapshot validity

valid_from_pcm_revision <= snapshot_revision
AND (
  valid_until_pcm_revision IS NULL
  OR valid_until_pcm_revision > snapshot_revision
)

파일을 staging에서 hash 검증한 후 immutable 최종 경로로 이동하고, 그 다음 DB transaction이 해당 파일을 참조하도록 한다. DB 실패 시 파일은 안전한 orphan이며 활성 지식이 되지 않는다.

ApplicationServices

DB pool, HTTP client, PCMReader, PCMWriter, model client는 서버 시작 시 구성하고 Graph runtime에 제공한다.

PCMToolContext

project_id, request_id, snapshot을 Tool factory에 바인딩한다. Tool 객체는 checkpoint state에 넣지 않는다.

현재의 module-level mock_service와 정적 Tool은 제거 대상이다. Issue Analysis Agent도 import 시 생성되는 singleton 대신 snapshot-aware factory가 실행 직전에 만든다.

Vertical slice 01

Markdown 한 건이 검색 가능한 지식이 되기까지

첫 구현은 문서 입력만 대상으로 한다. Repository 분석을 미루고도 PCM의 핵심 위험인 자동 지식 갱신, revision, provenance, embedding, hybrid search, request-scoped Tool을 한 번에 검증한다.

구현 상태: Domain model, Reader·Writer Protocol, 결정적 in-memory PCM, Markdown Source parser, 기존 CLIO_LLM 설정을 재사용하는 Knowledge model, topic 추출·후보 검색· change-set 검증·commit 파이프라인, document_added Root Graph 연결, PostgreSQL·pgvector Docker 구성, immutable Markdown 영속 저장, heading-aware chunking, local embedding 기반 pgvector, FTS·trigram·RRF hybrid retrieval과 index backfill, request-scoped Agent Read Tools, Issue Analysis Graph 비동기 연결, Knowledge citation revision 검증, bare Git mirror, commit-bound Repository 탐색 Tool과 Repository citation 검증, bounded code source 수집, architecture·component·operation Knowledge 자동 생성과 commit provenance까지 구현되었다. 다음 구현 단위는 해결된 이슈를 PCM 지식으로 되먹임하는 pipeline이다.

End-to-end 시나리오

  1. API가 document_added 요청과 정규화 Markdown을 전달한다.
  2. Graph가 event를 멱등하게 등록하고 base PCM snapshot을 고정한다.
  3. Source Markdown을 immutable revision 파일로 저장한다.
  4. heading section을 Source Unit으로 파싱하고 topic을 구조화 추출한다.
  5. 각 topic에 대해 기존 Knowledge를 hybrid 검색한다.
  6. LLM이 create, update 또는 no-change 결정을 반환한다.
  7. Service가 reference와 revision을 검증하고 PCM commit을 수행한다.
  8. 변경된 Markdown을 chunking하고 keyword·vector index를 갱신한다.
  9. 새 snapshot에서 Agent Tool이 지식을 검색하고 전체 내용을 읽는다.

Failure semantics

자동화는 실패를 숨기지 않는다

실패동작사용 가능한 상태
동일 event 재수신기존 완료 결과 반환기존 PCM 유지
LLM timeoutevent를 retryable로 기록기존 PCM 유지
잘못된 change set검증 오류를 포함해 1회 재생성commit 전이므로 기존 PCM 유지
base revision 충돌최신 snapshot에서 retrieval과 생성을 재실행stale change 저장 안 함
Markdown 저장 실패DB transaction 시작하지 않음기존 PCM 유지
Embedding API 실패index 재시도 큐, keyword 검색 사용새 Knowledge는 읽기 가능
Query embedding 실패keyword-only degrade검색 지속
모든 변경이 즉시 active라는 원칙은 “부분 결과도 활성화”를 뜻하지 않는다. 완전한 Knowledge commit만 active가 되고, vector index는 별도 revision으로 지연 상태를 명시한다.

Quality bar

테스트 가능한 완료 기준

핵심 통합 테스트

  • 새 문서가 하나 이상의 Knowledge로 생성된다.
  • 같은 주제의 다음 문서 revision이 기존 Knowledge를 갱신한다.
  • 같은 event를 두 번 실행해도 PCM revision은 한 번만 증가한다.
  • snapshot 42에서 revision 43 지식은 검색되지 않는다.
  • 모든 Knowledge fact가 Source Unit을 참조한다.
  • exact keyword와 semantic query 모두 같은 지식을 찾는다.
  • 검색 결과를 knowledge ID로 전체 읽을 수 있다.
  • 다른 프로젝트 Knowledge가 결과에 섞이지 않는다.

완료 Definition of Done

  • Mock Service 없이 slice가 실제 storage adapter를 사용한다.
  • 외부 모델 호출은 fake로 대체해 결정적 테스트가 가능하다.
  • 실제 API smoke test는 opt-in marker로 분리한다.
  • DB·파일·index 결과를 모두 독립적으로 검증한다.
  • Tool 입력에서 project와 revision을 지정할 수 없다.
  • 모델 key와 Source 내용이 로그에 남지 않는다.
  • pytest, ruff check, format 검사를 통과한다.
