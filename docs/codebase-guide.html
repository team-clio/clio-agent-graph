Clio Agent Graph 지도

이 프로젝트는 요청 종류에 따라 여러 LangGraph workflow를 실행하는 Python Agent Server입니다. 이 문서는 “어디부터 읽고, 어느 코드가 무엇을 책임지는지”에 초점을 맞춘 코드베이스 안내서입니다.

Python 3.11+LangGraphPydantic contractsPCM · Git · Retrieval
한 문장 모델요청 흐름폴더 지도주요 workflow계층과 경계읽는 순서현재 변경

01 · Mental model

“요청 라우터 + 목적별 서브그래프 + 안전하게 분리한 도구와 서비스”

먼저 이 세 덩어리만 기억하면 됩니다. 루트 graph가 요청을 검증하고, 알맞은 workflow가 일을 순서대로 수행하며, Agent는 읽기 전용 Tool을 통해서만 프로젝트 정보를 봅니다.

1

Root Graph

graph.py가 request_type을 보고 작업 경로를 정합니다. API 진입점은 여기 하나입니다.

2

Subgraph와 Node

workflows/orchestration/graphs/는 흐름도, workflows/orchestration/nodes/는 각 단계에서 실제로 할 일을 담습니다.

3

Agent · Tool · Service

Agent가 판단·도구 선택을 하고, Tool이 권한 경계를 만들며, Service가 PCM·Git·DB 같은 기반 기능을 구현합니다.

처음엔 세부 AI 프롬프트부터 읽지 않아도 됩니다. graph.py → workflows/orchestration/requests.py → workflows/orchestration/graphs/ → workflows/orchestration/nodes/ 순서로 읽으면 실행 경로가 먼저 잡힙니다.

02 · Request lifecycle

모든 요청은 같은 입구에서
검증되고 분기됩니다

외부에서 들어오는 JSON은 Pydantic 모델로 검증된 뒤 공통 상태에 펼쳐집니다. 이후에는 각 workflow가 그 상태를 채워 결과를 만들고, 마지막에 공통 응답 형태로 정리됩니다.

04 · Main workflows

가장 중요한 두 workflow부터
따라가 보세요

Report Processing

버그 리포트를 받아 표준화하고, 과거 이슈 후보를 찾은 다음, 기존 이슈 연결·사람 검토·새 이슈 생성 중 하나를 결정합니다. 새 이슈일 때만 Issue Analysis를 재사용합니다.

load_and_normalize_report → search_issue_candidates → match_report → apply_match_decision

Issue Analysis

시작 시 PCM revision과 repository commit을 snapshot으로 고정합니다. 이후 문서·코드·이력을 병렬 탐색하고, 분석과 해결 계획을 만든 뒤 citation 품질을 확인합니다.

prepare_analysis → (3개 검색 병렬) → analyze_issue → plan_resolution → quality_gate

1prepare_analysis프로젝트 snapshot을 한 번 고정
→
2 · parallel문서 · 코드 · 이력 탐색서로 독립된 evidence를 동시에 수집
→
3analyze_issue읽기 Tool을 가진 Agent가 사실·근거를 정리
→
4quality_gatecitation과 revision 일치 여부를 검사

snapshot이 중요한 이유: 분석 중에 문서나 branch가 바뀌어도, 한 요청 안에서는 같은 PCM revision과 같은 Git commit만 보게 합니다. 결과의 근거를 나중에 재확인할 수 있습니다.

05 · Boundaries

AI에게는 판단을 맡기고,
쓰기와 권한은 코드가 통제합니다

이 프로젝트에서 가장 중요한 설계 규칙입니다. Node는 실행 순서를 책임지고, Agent는 읽기 Tool을 사용해 판단하며, write 작업은 Node가 Service를 직접 호출합니다.

N

Node

상태를 읽고 다음 호출을 조합합니다. 등록, commit, 저장처럼 부작용이 있는 작업도 Node에서 시작합니다.

T

Tool

Agent의 입력과 권한을 좁힙니다. PCM Tool은 project와 snapshot을 closure로 고정해 Agent가 임의 범위를 지정하지 못하게 합니다.

S

Service

Git, PostgreSQL, Markdown 저장소처럼 실제 인프라에 접근합니다. 테스트에서는 in-memory 구현이나 mock으로 바꿉니다.

주체가능한 일의도적으로 못 하는 일
Agent검색, 문서 읽기, 코드 탐색, 분석·계획 생성프로젝트 지식·이슈·repository를 직접 쓰기
Tool입력값 검증, snapshot 범위 고정, 안전한 결과 전달Agent에게 credential 또는 임의 파일 시스템을 노출
ServicePCM revision, Git mirror, 검색 index 관리Agent의 판단을 우회해 임의 업무 workflow를 결정

06 · First-week reading path

코드를 전부 읽기보다,
한 요청을 끝까지 따라가세요

처음에는 analyze_issue 요청 하나를 선택하는 것을 권합니다. 라우팅, 상태, 병렬 실행, Agent Tool, Service 호출까지 모두 볼 수 있는 대표 경로입니다.

입력 계약

workflows/orchestration/requests.py에서 AnalyzeIssueRequest의 필드를 읽습니다.

라우팅

graph.py와 workflows/orchestration/nodes/common.py에서 해당 request_type이 어디로 가는지 봅니다.

workflow

workflows/orchestration/graphs/issue_analysis.py에서 노드 순서와 병렬 구간을 확인합니다.

구현과 검증

workflows/orchestration/nodes/issue_analysis.py와 대응 테스트를 나란히 읽습니다.

테스트는 설계 문서에 가깝습니다. 예를 들어 tests/nodes/test_issue_analysis.py는 graph가 어떤 상태를 만들고, quality gate가 어떤 경우에 재시도·검토로 가는지 빠르게 보여줍니다.

07 · Safety model

Repository 접근은
안전하고 재현 가능해야 합니다

현재 구현은 외부 입력, 고정 commit, 비밀 경로, 삭제 범위를 코드 수준에서 제한합니다.

외부 입력과 삭제 안전성

Repository 등록 source_uri를 HTTPS URL로 제한하고 embedded credential을 거부합니다. 제거 시에는 이 프로젝트가 관리하는 bare mirror와 manifest만 idempotent하게 지웁니다.

Agent에 보이는 코드 탐색 표면

Issue Analysis Agent는 저수준 파일 목록·검색·읽기 Tool을 직접 받지 않고 explore_codebase 하나를 받습니다. 내부 explorer가 제한된 도구를 선택해 cited evidence를 돌려줍니다.

Snapshot-bound 파일 목록

list_repository_files가 추가되어 고정 commit의 tracked 파일을 제한적으로 나열합니다. secret 경로와 범위 밖 접근은 계속 차단합니다.

PCM reconciliation은 TODO

Repository lifecycle에서 repository-derived PCM knowledge를 ingest·삭제하던 처리는 제거됐습니다. 해당 정합화는 명시적인 후속 작업입니다.
